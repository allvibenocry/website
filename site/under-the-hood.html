Under the hood

How All vibe no cry is built, what has been tested and where, and what it does not protect against.

What this page is

A description of the software as it is in its repository today, and of what is planned. Every statement carries one of three labels.

Built
Built, and tested on the local test host: a disposable Debian 13 machine in a container on a workstation. Not yet run on real hardware, and not yet tried by the project's owner.
Verified on hardware
Built, and verified on a real Debian 13 machine. Nothing is marked this yet.
Planned
Decided, or named as later work, in the repository. Nothing of it is built.

Where things stand

BuiltAll vibe no cry is in development. Nothing here is ready to install on a machine that matters.

BuiltWhat exists is the operational core, as command-line tools: the host installer, projects with dev and prod, backups with restore checks, and releases with rollback. D11

Each statement traces to a file in the product repository, and most to a numbered decision, such as D22, which links to its entry. The fact sheet lists the source of every statement on this page.

The stack

One machine, one operating system, and Docker for everything a project runs.

  • BuiltDebian 13 on x86-64. The installer refuses anything else, and anything not run as root, before it changes anything. D8, D17
  • BuiltDocker Engine and its Compose plugin, from Docker's own repository. The installer first checks Docker's signing key against its published fingerprint. D9, D17
  • BuiltEverything a project runs is a Docker Compose stack, and every project has two: dev and prod. D9
  • BuiltOne nginx is the reverse proxy for the whole host: the unprivileged nginx image, on the host's network, with a read-only filesystem, every capability dropped, and no access log. D12, D27
  • BuiltIts configuration is generated, and nginx -t checks it before every reload. D12
  • BuiltPostgreSQL 18, one per environment: a project has two databases, one for dev and one for prod. D10, D27
  • BuiltThe command-line tool, allvibe, is TypeScript compiled to JavaScript. It runs on Debian 13's own Node.js package, 20.19.2, and uses only Node's standard library: it has no runtime dependencies, so installing it downloads nothing from npm. D11, D15, D32
  • BuiltIt runs as a service user of its own, allvibe, which owns everything the suite creates. D15
  • BuiltBackups are encrypted with age, from Debian's own package. D13
  • BuiltDocker hands out addresses from 172.20.0.0/14, or from 10.201.0.0/16 if that overlaps a network the machine is on. It keeps small rotating logs, and keeps containers running while Docker itself restarts. D16
  • BuiltEvery image the suite pulls is pinned by digest: PostgreSQL 18.6, Node.js 24.21.0 for the starter app, and nginx 1.30.5 for the proxy. A project's own images are built on the host. D27
  • BuiltA systemd timer runs the daily backup at 03:30, plus up to 30 random minutes, and catches up after the machine was off. The installer enables and starts it. D24
  • BuiltA new project starts as a guestbook: Node.js 24 with node:http, one dependency (the pg driver), migrations applied at start, and a /healthz that asks the database. D19
  • BuiltA project is reached at the host's address and a port: prod on 8100 plus two per project, dev on the port after it, up to 49 projects. No DNS, router or hosts file is changed. D18, D30
  • BuiltReaching a project from another machine on the home network has not been verified yet: on the test host, the ports are on the workstation's loopback only. D18
  • PlannedA control panel in the browser, which will show links, so that nobody types a port. D30

Dev and prod, kept apart

Dev is where changes are made. Prod holds the real data.

  • BuiltDev and prod share no network, no volume and no secret. D9
  • BuiltEach environment's database is on an internal network of its own, which Docker gives no route out. Its app is on that network and on an edge network of its own. D9
  • BuiltEach environment's data is its own named volume. D9
  • BuiltEach environment's database password is generated on the host, 32 random bytes, kept in a file, and mounted only into that environment's containers as a Compose secret. It is never printed, and never an environment variable. D21
  • BuiltApps publish their port on the host's loopback only. The proxy, on the host's network, is the only way in. D18
  • BuiltThe proxy listens on IPv4 only, so a global IPv6 address on the machine cannot put a project on the internet. D18
  • BuiltProd's front door refuses every address range Docker hands out on the host, read from Docker when the door is written. So no container, dev or otherwise, reaches prod, not even the way a browser on the home network does. D18
  • BuiltThat has been checked on the test host's Docker. On a real host, where Docker's default bridge usually has a different subnet, it has not been checked yet. D18
  • PlannedThe AI agent's own container, which will work in dev, is planned. Until it exists, dev is changed by hand. D28

The release pipeline

allvibe release <project> takes what dev runs to prod.

BuiltA release runs 13 steps, in order, and stops at the first that fails. The failure names the step and what would have to be true, and nothing after it runs. D25

  1. 1BuiltDev runs the commit being released, with nothing uncommitted, and answers its smoke check. D25
  2. 2BuiltThe recovery key has been confirmed. D13, D25
  3. 3 to 5BuiltThe backup target is off this machine and writable; prod's database is running; an encrypted backup of prod is written to the target. D22, D23
  4. 6 to 9BuiltA restore check of that very backup: it is whole and decrypts, it restores into a scratch copy, and the app's own health check passes against the copy. D23
  5. 10BuiltProd's new image is built from the commit through git archive, never from the working tree. D25
  6. 11, 12BuiltProd is deployed on the new version, and answers its smoke check. D25
  7. 13BuiltThe commit is tagged with the version, and the release is recorded with its commit, its backup and the version it replaced. D25

When it fails

  • BuiltIf step 11 or 12 fails, prod goes back to the version it ran before, automatically, keeping its data. The release is recorded as failed. D25, D26
  • BuiltA crash loop counts as a failure at once, and the failure shows the line in which the app said what went wrong. D25
  • BuiltVersion numbers are never reused, even after a rollback. D25
  • Built--dry-run runs every check and changes nothing. D25
  • BuiltEvery run of every operation is recorded, with its steps and, on failure, the reason. D24
  • BuiltTried on the test host: a change released with prod's entries intact; a release whose migration failed in prod, rolled back automatically with every entry; and a release stopped at the backup step with the backup disk gone, with nothing built, tagged or deployed. D26

Backups

Off the machine, encrypted, and restored before they count.

  • BuiltA backup goes only to a directory the suite can prove is off the machine, and it checks again before every backup: a disk that was there yesterday may be unplugged today. D22
  • BuiltOff the machine means, as the kernel sees it: not on the root filesystem, which is also where an unplugged disk leaves its empty mount point; not on the filesystem that holds Docker's data; not on the same physical disk as either, found through partitions, LVM and LUKS; a real disk, or a network share such as NFS or SMB; and writable by the service user, proven by writing a file as it. D22
  • BuiltReal disks have not been tried yet. On the test host, one mount point is declared a separate disk, and everything else still refuses. D14, D22

How a backup is written

  • BuiltEvery backup is encrypted to two keys: a host key, which stays on the machine and is what the daily restore check decrypts with, and a recovery key, whose private half the owner keeps off the machine. D13, D29
  • BuiltIt is pg_dump in its custom format, run inside prod's own database container so that client and server always match, and streamed straight into age. Nothing unencrypted is written to the target. D23
  • BuiltIt is written under a temporary name, flushed to disk, and only then renamed. A small manifest is written last: the time, the release, prod's entry count, the checksum, both public keys and the database image. A backup without a manifest is incomplete. D23
  • BuiltBackups taken for a release are kept, and never pruned. Others go after 30 days, but never the newest three, and only files the suite named itself. D23

How a restore check runs, without touching prod

  • BuiltIt verifies the checksum, and decrypts the whole file with the host key into a private temporary file, so a damaged backup fails before anything is restored. D23
  • BuiltIt restores into a scratch PostgreSQL of the same image, on a scratch internal network, and stops at the first error. D23
  • BuiltIt starts the version of the app the backup was taken from against the copy, and asks the app's own health check, which reads the data. It reports the entry count beside the count prod had when the backup was taken. D23
  • BuiltIt removes its containers, its network and the decrypted file, whatever happened. Nothing it creates shares a name, a network or a volume with prod. D23

Every day

  • BuiltEvery day, for every project: a backup of prod, then a restore check of that very backup. One project's failure does not leave the others without theirs. A failure makes the service fail, and shows up in allvibe doctor. D24
  • BuiltThe daily run has so far only been started by hand. One that happens on its own, at night, has not been seen yet. D24

Rollback and data

Code goes back. Data stays, unless you ask for it too.

  • Builtallvibe rollback goes back to the version prod ran when the current one was released, and changes only the code. Prod's data stays as it is, so nothing written since the release is lost. D26
  • BuiltWhy: the usual reason to roll back is that the new code is wrong, and what people wrote since the release is real. D26
  • BuiltEach migration runs in a transaction, so a migration that fails leaves the schema as it was. That is why the automatic rollback after a failed release kept every entry. D26
  • BuiltIf the older version cannot run on today's data, its smoke check fails, the rollback stops, and it names the other way: --restore-data. D26
  • Built--restore-data on its own changes nothing. It says what would be lost: the time the data goes back to, and how many entries prod has now against the backup. D26
  • BuiltWith --confirm-data-loss as well, it first takes a backup of prod as it is, then empties prod's database and restores the backup taken just before the current version was released, then deploys the older version and checks it. Even a confirmed mistake can be undone from that first backup. D26
  • BuiltA known gap: rolling back past a release whose migration succeeded runs the old code on a newer schema, and if the old code still answers its health check, the rollback counts as done. D31
  • PlannedTo close it: releases record their schema version; rollback explains, and offers --restore-data, when the database is newer than the version it goes back to; and the project template gets a rule that, within one release, migrations only add, never drop or rename. D31

Secrets and keys

What exists today, and what is planned.

Today

  • BuiltThe tools read secrets by name, from the environment or from files with restricted permissions, and never prompt for a password. D13, D21
  • BuiltA project's database passwords are files, generated on the host and mounted only where they are needed. D21
  • BuiltThe host key is made at install with age-keygen, stays on the machine, and only the service user can read it. D13
  • BuiltThe recovery key is made at install too. Its private half is written once, to a file only the service user can read, and is never printed. D13
  • BuiltThe owner copies it off the machine and hands it back with allvibe recovery-key confirm, on standard input: the command refuses a terminal rather than ask. If it matches, the copy on the machine is deleted, and the owner's is the only one. D13
  • BuiltUntil it is confirmed, every release is refused, and allvibe doctor reports it. Every 180 days, doctor asks to see it again. D13
  • BuiltRestoring on a new machine needs the recovery key and nothing else. D13
  • BuiltThe project's own repository is scanned for secrets on every push, over its whole history, and checked for details of anyone's infrastructure. D6, D7

Planned

  • PlannedA key check before every push, for the apps people build. D6
  • PlannedOnce there is a web UI, the recovery key as a download and as a printable recovery sheet. D29
  • PlannedWhen a recovery key is lost: a new one for future backups, with a clear warning that older backups open only with the old key. D29

Off-site backups

Out of the house, not only off the machine. All of it is planned.

  • BuiltToday a backup leaves the machine, but usually not the house. That protects against the computer dying, not against a fire, a theft or water. D22
  • PlannedA backup target becomes a type, not a path: a local disk as today, an rclone remote, or S3-compatible storage. The backup format already works for any of them.
  • PlannedSeveral targets at once. A release still needs only the local backup. The off-site copy is sent in the background and raises an alert when it falls behind, so an internet outage never blocks a release.
  • PlannedThe options, simplest first: two disks, rotated between home and somewhere else, with a reminder; cloud storage you already have, through rclone; S3-compatible object storage; and later, perhaps, a friend's machine.
  • PlannedOff-site credentials that can write but not delete, so that a compromised machine or a misbehaving agent cannot destroy the off-site copies.
  • PlannedAn occasional restore check of an off-site copy, downloaded and tested the same way as the local one.
  • PlannedThe storage provider only ever sees encrypted files, because backups are encrypted on the machine before anything leaves it. D13

PlannedKeep the recovery key outside the house as well. After a fire, an off-site backup is useless if the only copy of the recovery key burned with the laptop. D29

What it does not protect against

Stated plainly, so that nobody has to find out.

  • A bug that passes the health check

    BuiltA release checks that the new version starts and answers /healthz, which says the app is up and can read its database. A bug anywhere else is released. D19, D25

  • A stolen computer

    BuiltProd's data is in a Docker volume on the computer's own disk, and the suite does not encrypt that disk: none of the installer's eleven steps does. Backups are encrypted, but the host key that opens them is on the same computer, so whoever takes the computer and its backup disk has both. D13

  • A fire, a flood or a theft that takes the backup disk too

    BuiltBackups leave the machine, not the house, until off-site backups exist. D22

  • An app's own weaknesses

    BuiltThe suite does not add sign-in to an app, or check the one it has, and the starter guestbook has none. Today nothing is published to the internet. Publishing is planned, and an app published with weak sign-in will be as open as its sign-in. D18, D28

  • What was written since the last backup

    BuiltThe scheduled backup runs once a day, and a release takes one first. A disk that dies in between takes with it what was written since. D24, D25

  • A backup that restores, but not completely

    BuiltA restore check proves that the app can read the restored copy, and compares the entry count. It does not compare every row. D23

  • Two operations at the same time

    BuiltNothing locks one against another yet. The nightly backup and a release started in the same minute would both run: nothing would be lost, but the work would be done twice. D28

The house rules

The rules the product is built to, quoted as they are written in its CLAUDE.md. Under each, what keeps it, and its label.

  1. The agent never reaches prod. Nothing in a dev environment has network access to, credentials for, or volumes of a prod environment.

    BuiltKept by the separation of dev and prod. The agent that will work in dev is planned.

  2. No release without a fresh backup on a target outside the machine's own disk, and that backup must have passed a restore test.

    BuiltKept by steps 3 to 9 of every release.

  3. The control panel is never exposed directly to the internet. There is no panel yet; the rule is recorded now.

    PlannedKept by the panel, when it exists.

  4. Secrets never appear on a command line, in output, in logs, in the repo or in a chat. Tools read them by name from the environment or from files with restricted permissions, and never prompt for a password. SSH is key-based with BatchMode=yes.

    BuiltKept by secrets in files, and nothing that prompts.

  5. Everything a beginner needs to do must eventually be doable in a browser. The CLI is the engine the web UI will call, not the user interface.

    PlannedKept by the web UI, when it exists.

  6. Every numbered item is tried by a human before it counts as done. Reports keep what was actually run and observed apart from what was only built.

    BuiltKept by the project's record of what has been tried, and by whom. Nothing has been tried by the owner yet.

  7. Stop at the first failure. An operation that fails part-way names the step and what would have to be true, and takes no further steps.

    BuiltKept by every operation running as steps.

  8. Rollback never loses data silently. If a rollback would discard data written since the release, it says so and requires explicit confirmation.

    BuiltKept by rollback keeping the data.

  9. Nothing is ever named "nocry": no command, process, service, container, image, package or file. "NoCry" is the name of a ransomware family, and a service that runs around the clock on people's home computers must not share a name with one. node scripts/guard.mjs checks it.

    BuiltKept by the project name rule and by the repository's guard. D2

BuiltRules 10 and 11 are about how the repository itself is kept: no details of anyone's infrastructure in it, and no rewriting of its history. D7
